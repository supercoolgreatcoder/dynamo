# Nix-built component-pipeline mocker parity

This campaign reruns the four split-pipeline gateway arms and the stock Dynamo
frontend reference with mock workers, all inside vCluster namespace
`dynamo-components-v2`. The AGW, Envoy, dynamic module, and Dynamo facade
executables came from `supercoolgreatcoder/dynamo-nix-envs` branch
`feat/dynamo-component-pipeline-builds`, commit `e62908ae661c2bd44c846164d5585f9141b7037a`.
That flake pins this Dynamo component source to `e00795406702d1d1c68b303334ce459256dc7f0f`.
The installed bundle was
`/nix/store/bw90rqrrihx2jnjwxhhwbkb8j7j7qj0r-dynamo-component-pipelines-e007954067`.

Each cell used six AIPerf 0.12.0 clients, concurrency 128 per client, 45 seconds,
and a 3/3 split across two dedicated CPU nodes. Four preprocessor Pods used the
`fastokens` backend, 16 mock workers were spread over four nodes, and one gateway
replica served each arm. For the stock Dynamo reference, one frontend and four
reference Pods hosted 16 logical `dynamo.mocker` workers. The split pipeline's
`benchmark-worker` is a benchmark-only synthetic `ServiceEngine` that emits a
fixed token stream; it does not perform Dynamo mocker's KV bookkeeping. Thus the
four gateway arms are same-backend comparisons, while the stock frontend point
is an architectural reference, not a strictly identical-backend A/B. Production
worker facades take a caller-supplied Dynamo backend engine rather than this
synthetic implementation. The benchmark client did not
tokenize or synthesize prompts during measurement: short and ISL4000 used frozen
OpenAI raw-payload JSONL, while Mooncake used the prepared content-addressed
mmap cache. The short and ISL4000 dataset SHA256 values are respectively
`ab030551a31fb4ac8e7a864a940862a68bc0d386b152b4aba7bc249322833426`
and `3ad382586f5417f4255d7eea774700d9817bc39acbc7b537e2efa7d89145c743`.
The normalized Mooncake trace SHA256 is
`28a94e9bc1b63fdc88e5217bdd5c647a0487c08c83bdc64a814ec0840562f550`.

The stock frontend used `fastokens`, a 64 MiB tokenizer cache, block size 512,
and 16 Dynamo runtime worker threads. Its discovery backend was etcd; request
and response transport were TCP and the event plane was ZMQ. NATS was scaled
to zero. This reference exercises the stock HTTP frontend and is not a gRPC
facade arm. Each benchmark Job used a shared wall-clock start barrier to limit
staggered trace replay; a Job is excluded if its Pods miss that barrier.

Job's six AIPerf JSON exports. All gateway cells have three valid zero-error,
non-cancelled Jobs. The stock Mooncake point is only one valid Job and is
**not a three-run median**.

Raw summary exports (JSON, CSV, and console text) live under
[`raw_aiperf/`](raw_aiperf/), grouped by Job name
`nixv2-{short|isl4000|mooncake}-{arm}-rN`. The first valid AGW static Mooncake
run is `r2`: its `r1` Job failed before sending traffic because the template
passed two aliases of AIPerf's export-level option. The template was corrected;
the failed Job is excluded. The per-request diagnostic logs remain on vCluster
NFS under `/shared/aiperf/results/<job>/{0..5}` and are not committed.
`nixv2-mooncake-dynamo-reference-r2` also completed but is excluded from
valid-trial medians: one client reported one AIPerf
`MemoryMapSerializationError` while decoding a conversation, and another
reported one empty-content `InvalidInferenceResultError`. Its six summary
exports remain in `raw_aiperf/` for audit; a replacement is required. No frontend
error or warning was found in the last 200 frontend log lines around that run;
the empty-content event's cause remains unproven.
The next stock reference Mooncake run, `r3`, also completed with two
empty-content `InvalidInferenceResultError` requests and is excluded. The
gateway-arm Mooncake runs had no such errors. A separate records-level
diagnostic is needed before accepting additional stock reference repeats.

The normalized Job-level metrics, failure counts, and ranges are in
[`benchmark_summary.json`](benchmark_summary.json), generated by
[`summarize-nix-mocker-results.sh`](../../summarize-nix-mocker-results.sh).
[`benchmark_execution.json`](benchmark_execution.json) snapshots the 47
completed benchmark and diagnostic Jobs, including applied commands, images,
node-affinity rules, timestamps, and observed Pod placement where retained.
It was reconstructed **after** execution, not recorded before each Job. Eleven
older Jobs had already lost complete Pod placement evidence, and the summary
export level does not retain per-request records. There was no immutable
pre-run benchmark plan for this custom gateway campaign. These are therefore
reproducible summary-level observations, not a formal promotion-grade AIPerf
comparison.

Mooncake offers about 3,026 requests per second at six clients, so the ~3,020
RPS values indicate trace-rate parity, not a gateway throughput ceiling. The
Envoy callout short median, 11,215.71 RPS, is 0.5% below the retained
11,272.38 RPS prototype reference, but that earlier run is not a paired
three-repeat series. AGW static's ISL4000 median is 35% below AGW generic's,
and Envoy direct's is 37% below Envoy callouts'. Their high effective
concurrency and latency warrant isolated transport-path experiments; the
matrix does not by itself establish root cause. Prior prototype references and
benchmark caveats are documented in
[`../2026-09-23-callout-parity.md`](../2026-09-23-callout-parity.md).
The older September 22 short/ISL4000 campaign used structured AIPerf generation,
so its numbers are not a same-series comparison to these frozen raw-body runs.
Even the short/ISL4000 points are achieved throughput, not a proven gateway
ceiling: for example, AGW static short `r3` had 12,600.76 aggregate RPS, but
the six clients' AIPerf `effective_concurrency.avg` values sum to 235.28
requests in flight versus 768 configured slots. Their throughput times mean
request latency independently agrees with that figure. A separate
load-generator scaling sweep is needed to locate the gateway knee.
